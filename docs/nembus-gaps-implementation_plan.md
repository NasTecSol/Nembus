# Nembus — Full Implementation Plan
## Closing All Gaps vs SAP Business One / S4HANA

> **Goal:** Elevate Nembus from a POS-centric platform with ERP-shaped tables into a fully operational,  
> SAP-standard ERP with a real double-entry accounting engine, complete procurement-to-pay,  
> order-to-cash, inventory control, and compliance — all excluding HR/Payroll.

---

## Architecture Conventions

Every new module follows the existing layered pattern:

```
packages/core/db/schema/        ← PostgreSQL DDL (numbered migration files)
packages/core/queries/          ← SQLC .sql files (one per domain)
packages/core/repository/       ← Auto-generated by sqlc generate
packages/core/usecase/          ← Business logic (the most important layer)
packages/core/handler/          ← HTTP handlers (thin, no logic)
packages/core/routing/          ← Route registration
apps/cloud-server/main.go       ← Wire UC + register routes
```

All automated posting (journal entries, stock movements, status transitions) lives in the **usecase layer** — never in the handler.

### 1.3 — Accounting Engine Use-Case

**File:** `packages/core/usecase/accounting_usecase.go` *(NEW)*

| Method | Purpose |
|--------|---------|
| `PostJournalEntry(ctx, tx, input)` | Core double-entry post — must run inside caller's DB transaction |
| `ValidateBalance(lines)` | Enforce sum(debits) == sum(credits) before committing |
| `ReverseJournalEntry(ctx, entryID, reason)` | Mirror-image reversal entry |
| `GetTrialBalance(ctx, orgID, periodID)` | All accounts: opening + debits + credits + closing |
| `GetAccountLedger(ctx, accountID, from, to)` | Per-account transaction history |
| `RunPeriodClose(ctx, orgID, periodID)` | Lock period, roll balances to next |
| `GetProfitAndLoss(ctx, orgID, from, to)` | Revenue - COGS - Expenses |
| `GetBalanceSheet(ctx, orgID, asOf)` | Assets = Liabilities + Equity |
| `GetCashFlowStatement(ctx, orgID, from, to)` | Operating / Investing sections |

> **Critical Design Rule:** `PostJournalEntry` is always called **within the same `pgx.Tx`** as the triggering document. If the journal fails, the entire operation rolls back atomically.

### 1.4 — Auto-Posting Map

| Business Event | Debit | Credit | Wired Into |
|----------------|-------|--------|------------|
| POS cash sale | Cash Account | Revenue + VAT Payable | `pos_usecase.go → CreateTransaction()` |
| POS card sale | Card Receivable | Revenue + VAT Payable | same |
| POS COGS | COGS Account | Inventory Account | same |
| Sales return (cash) | Sales Returns | Cash Account | `sales_return_usecase.go → ApproveReturn()` |
| Sales return (stock) | Inventory Account | COGS Account | same |
| GRN posted | Inventory Account | GR/IR Clearing | `goods_receipt_notes_usecase.go → PostGRN()` |
| Supplier invoice | GR/IR Clearing + WHT Recv | AP Account + Input VAT | `supplier_invoice_usecase.go → PostInvoice()` |
| Supplier payment | AP Account | Bank/Cash Account | `supplier_invoice_usecase.go → PayInvoice()` |
| Customer invoice | AR Account | Revenue + Output VAT | `invoice_usecase.go → PostInvoice()` |
| Customer payment | Bank/Cash Account | AR Account | `invoice_usecase.go → RecordPayment()` |
| Stock adjustment | Inventory / Variance | Variance / Inventory | `inventory_stock_usecase.go → AdjustStock()` |
| Stock count variance | Inventory / Variance | Variance / Inventory | `stock_count_usecase.go → PostCount()` |
| Depreciation run | Depreciation Expense | Accumulated Depreciation | `asset_usecase.go → RunMonthlyDepreciation()` |

### 7.3 — Analytics Materialized Views

Replace app-level inserts into analytics tables with PostgreSQL materialized views + scheduled `REFRESH MATERIALIZED VIEW CONCURRENTLY`:

```sql
CREATE MATERIALIZED VIEW mv_daily_sales AS
SELECT
    pt.store_id, ptl.product_id,
    DATE(pt.transaction_date) AS sale_date,
    SUM(ptl.quantity) AS units_sold,
    SUM(ptl.line_total) AS revenue,
    SUM(ptl.discount_amount) AS discounts,
    SUM(ptl.tax_amount) AS taxes,
    COUNT(DISTINCT pt.id) AS transactions
FROM pos_transactions pt
JOIN pos_transaction_lines ptl ON ptl.transaction_id = pt.id
WHERE pt.status = 'completed'
GROUP BY pt.store_id, ptl.product_id, DATE(pt.transaction_date);

CREATE UNIQUE INDEX ON mv_daily_sales(store_id, product_id, sale_date);
```

## Verification Plan

### Phase 1 (Accounting Engine)
- Post a POS transaction → assert `journal_entries` row exists with `SUM(debit) = SUM(credit)`
- Query `trial_balance` endpoint → confirm total debits = total credits across all accounts
- Run period close → assert `fiscal_periods.status = 'closed'` and next period `opening_balance` = prior `closing_balance`
- Reverse a JE → assert reversal entry created and original status = 'reversed'

- AP aging report buckets verified against invoice due dates

## Open Questions for Your Review

> [!IMPORTANT]
> **Q1 — Costing Method:** Should Nembus default to **AVCO** (weighted average cost) for all items, or allow per-item selection? SAP B1 defaults to AVCO. Standard Cost is only needed for manufactured goods which we're not doing — so AVCO-only is recommended.

> [!IMPORTANT]
> **Q2 — GL Chart of Accounts Seed:** Should we ship a **default Saudi CoA** (aligned with SOCPA standards) that gets auto-seeded on org creation, or should the customer configure their own accounts? Recommend: ship a standard template that can be customized.

> [!IMPORTANT]
> **Q3 — Fiscal Year Type:** Gregorian (Jan–Dec) or Hijri? Most Saudi businesses report on Gregorian but some use Hijri. Recommend: Gregorian as default with optional Hijri display.

> [!WARNING]
> **Q4 — WHT (Withholding Tax):** KSA mandates WHT on certain service payments to non-residents. Should WHT be included in Phase 2, or deferred? Recommend: include in Phase 2 since it affects supplier payment posting.

> [!WARNING]
> **Q5 — Negative Stock Policy:** Should the system **hard-block** sales when stock = 0, or **allow negative stock with a warning** (useful for high-volume POS environments)? Recommend: configurable per org — `allow_negative_stock BOOLEAN` on `organizations`.

> [!NOTE]
> **Q6 — Restaurant Module Gaps:** Phase plan does not include restaurant-specific gaps (recipe costing, floor plan editor, split bill, delivery integrations). Should these be added as **Phase 8**?

> [!NOTE]
> **Q7 — Execution Model:** Should phases run sequentially (one team, complete + test before next) or in parallel streams (Phase 1 accounting + Phase 4 inventory simultaneously by separate developers)?
